# AGENTS.md

Guidance for AI agents and automation working in this repository.

## Operating Prompt

You are working on `gdo-blaq-homekit`, an ESP-IDF firmware project that makes the Konnected GDO blaQ act as a native Apple HomeKit garage door accessory. Treat changes as embedded, networked, and safety-relevant: garage door movement, lock state, obstruction state, HomeKit pairing, Wi-Fi credentials, and rolling-code behavior all have real-world effects.

Before changing files, classify the task:

- **Docs or metadata only:** edit the requested docs/scripts and do not run firmware commands unless needed.
- **Firmware behavior:** inspect the relevant `main/` files and validate with an ESP-IDF build when the toolchain and submodules are available.
- **HomeKit behavior:** verify characteristic constants, value types, pairing/setup implications, and event ordering.
- **Hardware actions:** do not flash, erase NVS, reset HomeKit data, or run monitor commands unless the user explicitly asks and hardware context is clear.
- **Release/CI:** preserve the GitHub Actions artifact, S3, and esp-web-tools manifest flows unless the task specifically changes them.

## ESP-IDF 6 Migration Notes

- Primary references for this migration are the ESP-IDF v6.0.1 release notes database entry at `https://release-notes.espressif.tools/release/6.0.1` and the official ESP-IDF 5.5-to-6.0 migration guide.
- ESP-IDF 6 splits several dependencies that older code often reached through transitive or aggregate components. Declare `esp_event`, `esp_netif`, `esp_driver_gpio`, and `esp_driver_uart` explicitly where used.
- The legacy `wifi_provisioning` dependency is not required by this app and should not be reintroduced unless provisioning behavior is being deliberately changed. ESP-IDF 6 moved that flow to the external `espressif/network_provisioning` component, but this firmware currently provisions Wi-Fi through `nvs_wifi_connect`.
- ESP-IDF 6 uses mbedTLS 4, where low-level headers such as `mbedtls/aes.h`, `mbedtls/sha1.h`, `mbedtls/sha256.h`, and `mbedtls/sha512.h` are no longer available to component code. The HomeKit platform MFi AES/SHA wrappers in this branch use PSA Crypto instead.
- `esp-homekit-sdk` legacy MFi I2C support depends on removed legacy I2C driver headers. Under IDF 6, do not build `esp_mfi_i2c.c` unless it is first ported to the new I2C driver APIs.
- This branch contains compatibility commits inside submodules. Before sharing or merging, those submodule commits need to be pushed to fetchable remotes and the superproject gitlinks need to reference those pushed commits.

## Behavioral Guardrails

- Treat garage door open/close and lock/unlock commands as safety-sensitive. Do not add automatic movement, retry loops, or state changes without explicit intent and clear bounds.
- Treat GDO learn mode, paired-device clearing, protocol selection, client ID changes, rolling-code changes, command interval changes, and toggle-only mode as high-risk. `gdolib` exposes APIs for them, but this firmware currently uses only a narrow subset at runtime.
- Keep GDO event handling lightweight. The existing pattern is: `gdolib` callback logs and calls `notify_homekit_*`; HomeKit characteristic updates happen through `gdo_notif_event_q` in `homekit_task_entry`.
- Be careful with queue behavior. `gdo_notif_event_q` is depth 16 and notification sends are non-blocking; frequent new events may be dropped unless the queue strategy is changed deliberately.
- Preserve Wi-Fi/HomeKit initialization ordering. `app_wifi_init()` is called after HomeKit setup because HomeKit installs event handlers and ordering matters.
- Do not enable the commented `hap_reset_homekit_data()` block unless the user explicitly asks to reset pairing data.
- Do not change `hap_set_setup_code("251-02-023")`, `hap_set_setup_id("KCTD")`, the provisioning AP SSID `konnected-blaq-hk`, or accessory identity fields unless the task is specifically about provisioning, pairing, or branding.
- Do not change GPIO pins or UART settings casually. Current GDO config uses inverted UART on `UART_NUM_1`, TX `GPIO_NUM_1`, RX `GPIO_NUM_2`, obstruction input `GPIO_NUM_5`, and `obst_from_status = true`.
- Be cautious with rolling-code sync behavior in `gdo_event_handler`. It currently allows at most three automatic rolling-code recovery jumps of 100 per boot before leaving the value unchanged. Any change here can affect opener pairing and security behavior.
- `gdo_get_status()` is documented as running in a critical section. Do not call it from hot paths or long-running logic without a clear reason.
- Keep `sdkconfig.defaults` as the committed configuration source. Do not commit generated `sdkconfig`, `sdkconfig.old`, `managed_components/`, `build/`, or `.cache/`. The root `dependencies.lock` is currently ignored; if release reproducibility becomes the task, decide explicitly whether to track it or tighten managed component pins.
- Avoid editing submodule contents directly for ordinary app work. This IDF 6 migration branch intentionally patches submodule code; keep those edits isolated in submodule commits and make sure the commits exist on a fetchable remote before relying on the superproject branch for reproducible builds.
- Do not add secrets or credentials. CI references AWS and GitHub secrets; keep values in the platform secret store.

## HomeKit Notes

- Current services: garage door opener, motion sensor, and lightbulb.
- The garage door service includes optional current/target lock characteristics.
- HomeKit setup values are hardcoded in `main/homekit.cpp` and documented in `README.md`.
- This project uses the open-source Espressif HomeKit SDK. Do not assume MFi factory-NVS provisioning, Home app Wi-Fi provisioning, or commercial certification behavior unless the task explicitly introduces it.
- `device_name` and `serial_number` are derived from the ESP MAC address at boot.
- Map GDO door states through `map_gdo_to_homekit_state()` instead of duplicating HomeKit numeric values.
- Use constants from `homekit_decl.h` when adding or comparing HomeKit characteristic values.
- When changing write callbacks, verify both the HomeKit write status and the local GDO command. Invalid writes must not be reported as success.

## Wi-Fi Notes

- `nvs_wifi_connect()` reads saved Wi-Fi mode and credentials from NVS. If the first connection fails or NVS has no data, the component starts SoftAP mode.
- `nvs_wifi_connect_start_http_server(...)` starts the Wi-Fi configuration web server. AP/fallback mode uses `NVS_WIFI_CONNECT_MODE_RESTART_ESP32`; STA mode uses `NVS_WIFI_CONNECT_MODE_STAY_ACTIVE`.
- Project defaults override the component defaults: configuration page URI `/`, websocket URI `/ws`, HTTP port `8080`, and SoftAP SSID `konnected-blaq-hk`.
- The provisioning docs point users to `http://192.168.4.1:8080/` in AP mode and `http://<device-ip>:8080/` in STA mode. If the URI, AP SSID, port, restart mode, or AP authentication changes, update `README.md` too.
- The dashboard polls `/api/status` and exposes device/GDO/Wi-Fi/heap/build data. `POST /api/gdo/refresh` must remain read-only unless the user explicitly asks for web-based control and the safety model is revisited.

## Reliability Notes

- `main/app_health.cpp` starts a health supervisor task after GDO startup. It logs the reset reason, subscribes to the ESP-IDF task watchdog, feeds it every second, requests Wi-Fi reconnects, periodically probes GDO status, and reboots only after sustained Wi-Fi or GDO failure.
- The health supervisor must not actuate the door. Use read-only status requests for health checks and keep reboot thresholds conservative to avoid false recovery loops.
- `sdkconfig.defaults` intentionally enables task-watchdog panic/reboot. If task priorities, blocking loops, or watchdog timing change, verify with a real-device smoke test.

## Firmware Style

- Follow the existing ESP-IDF style: `ESP_ERROR_CHECK` for required startup operations, `ESP_LOGI/ESP_LOGE` with local tags, and small FreeRTOS task/callback functions.
- Prefer explicit state mapping and typed enums over raw numeric literals.
- Keep blocking work out of callbacks and event handlers.
- Keep memory use conservative. This firmware runs on a 4MB flash ESP32-S3 target with a single large app partition.
- Treat IRAM as critically constrained. The validated `idf.py size` run reported 0 bytes free in IRAM. Avoid adding IRAM-resident code, interrupt handlers, or config changes that move code into IRAM without checking size.
- Use C++ features conservatively; the surrounding code is C-style ESP-IDF C++.
- Add comments only for non-obvious ordering, hardware, protocol, or safety constraints.


```sh
python tests/hardware_smoke.py --port /dev/cu.usbmodemXXXX --build --flash --erase-flash --expect-wifi ap
```

## Review Checklist

Before finishing any firmware change, check:

- Does this affect physical door movement, lock state, obstruction reporting, or rolling-code sync?
- Are HomeKit current and target states mapped correctly and updated from the right task context?
- Does Wi-Fi provisioning still fall back to the `konnected-blaq-hk` AP and `http://192.168.4.1` flow?
- Did any generated files, build artifacts, local SDK config, or submodule internals change?
- Did CI build assumptions remain aligned with ESP-IDF `v6.0.1`, target `esp32s3`, 4MB flash, and the combined binary offsets?
- Did `idf.py size` still leave acceptable app partition and IRAM headroom?
